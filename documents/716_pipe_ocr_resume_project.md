# 连云港中船 716 所工业质检 Agent 项目

## 简历项目写法

**项目名称：** 连云港中船 716 所钢管文字与形状识别智能质检 Agent  
**所属单位：** 中船 716 所  
**项目周期：** 2025.03 - 2025.10  
**目标岗位：** AI Agent 开发工程师 / LLM 应用开发工程师 / 工业智能体开发工程师  
**技术栈：** Python、PaddleOCR、PaddlePaddle、Flask、OpenCV、DeepSeek-V4-Flash、ReAct、Agentic RAG、状态机、Tool Calling、ERP/BOM 校验、JSONL/CSV 持久化、Git/GitHub、NVIDIA Jetson TX2、CUDA 11.8、cuDNN 8.9

**项目简介：**  
该项目面向船舶制造场景下钢管等中大型构件的智能质检需求，在原有 PaddleOCR 视觉识别能力基础上，进一步重构为具备“感知、推理、校验、行动、记忆”的工业质检 Agent。系统将 OCR 字符识别、形状分析、ERP/BOM 查询、工艺变更 RAG 审查、告警通知和装配仿真预备封装为可调用 Tools，并基于 ReAct 状态机编排 Agent 执行链路。针对工业现场手写字符潦草、OCR 低置信度、物料号易混淆等问题，引入 DeepSeek-V4-Flash 作为语义级 OCR 纠错模型；同时构建轻量级 Agentic RAG，在 BOM 校验通过后动态检索最新工艺变更单、质检补充通知等非结构化文档，判断是否需要复检、禁装或人工审核。

## 个人职责

1. 负责将原有 PaddleOCR 视觉识别系统重构为工业质检 Agent 架构，完成从“被动识别 API”到“主动决策智能体”的项目升级。
2. 设计 Agent 四层架构：认知中枢、感知工具箱、行动工具箱、记忆与持久化模块，实现模块解耦和工具化调用。
3. 基于 ReAct 思路设计状态机工作流，编排 `Trigger -> Perception -> Reasoning -> Validation -> Decision -> Action` 的完整执行轨迹。
4. 将 OCR 文字识别、形状识别、ERP/BOM 查询、飞书/钉钉告警、装配仿真预备等能力封装为 Agent Tools，统一工具输入输出协议。
5. 接入 DeepSeek-V4-Flash，设计语义级 OCR 纠错工具 `Tool_Semantic_OCR_Correction`，用于低置信度 OCR 或 ERP 查无物料场景。
6. 设计 LLM 结构化输出 schema，要求模型返回 `corrected_text`、`confidence`、`reason_summary`、`candidates_considered` 等字段，保证纠错过程可审计。
7. 实现 BOM 二次校验机制：原始 OCR 查无物料时触发 LLM 纠错，纠错置信度达标后重新查询 ERP/BOM，再决定放行或告警。
8. 构建轻量级 Agentic RAG，支持从本地工艺文档目录检索临时工艺变更单、质检补充通知等非结构化文本，并交由 LLM 判断是否覆盖当前物料放行规则。
9. 实现“BOM 通过后仍需 RAG 审查”的安全闸门：当最新工艺通知要求复检或禁装时，Agent 会覆盖常规放行路径，触发告警并挂起等待人工审核。
10. 设计短期记忆机制，记录当前批次和工位已识别构件，降低同一钢管重复识别和重复告警风险。
11. 实现长期轨迹持久化，将 Agent 每次工具调用、推理结果和决策状态写入 JSONL，便于后续审计和问题追溯。
12. 实现 CSV 报表导出规范，对时间戳、批次号、超长物料 ID 等字段强制文本化序列化，避免 Office 打开后自动转成科学计数法造成数据失真。
13. 编写单元测试覆盖正常放行、BOM 异常告警、语义 OCR 纠错、工艺变更 RAG 拦截、CSV 文本保护和 DeepSeek 接口路径等核心链路。

## Agent 架构设计

### 1. 认知中枢 Controller Agent

Controller Agent 负责接收全局任务，例如“盘点当前车间 A 区钢管物料准备情况”，并按状态机拆解为感知、推理、校验和行动步骤。当前实现中，规则状态机承担确定性流程控制，LLM 负责传统规则难以处理的语义纠错场景。

核心文件：

```text
agent/controller.py
agent/brain.py
agent/state_machine.py
```

### 2. 感知工具箱 Perception Tools

感知工具负责对现场构件进行底层识别：

```text
Tool_Read_Pipe_Text      # 调用 OCR 服务读取钢管文字
Tool_Analyze_Shape       # 分析构件形状、直径、法兰等参数
```

这些工具将原有 PaddleOCR 和形状识别能力从业务逻辑中剥离出来，使其成为 Agent 可调用的标准能力。

### 3. 推理工具箱 Reasoning Tools

推理工具负责处理需要 LLM 常识和上下文理解的问题：

```text
Tool_Semantic_OCR_Correction
Tool_Process_Change_RAG_Check
```

触发条件：

```text
OCR 置信度低于阈值
或
ERP/BOM 首次查无精确物料
```

示例：

```text
OCR 原始结果：0345B-DN5OO
LLM 语义纠错：Q345B-DN500
纠错依据：Q/0、O/0 视觉相似；Q345B 是船舶与钢结构场景常见材料牌号；DN500 符合管径命名规范；BOM 候选项存在 Q345B-DN500
```

### 4. Agentic RAG 工艺变更审查

RAG 工具负责读取临时工艺变更单、质检补充通知等非结构化文档：

```text
Tool_Process_Change_RAG_Check
```

典型场景：

```text
OCR 识别：316L-DN500
BOM 校验：一致，按常规规则可放行
RAG 检索：命中当天发布的《7 号船坞海水冷却管线替换临时通知》
LLM 判断：该通知要求所有 316L 管材送二号实验室超声波复检，禁止直接装配
Agent 决策：blocked_by_process_change，触发告警并挂起人工审核
```

### 4. 行动工具箱 Action Tools

行动工具用于连接外部业务系统：

```text
Tool_Query_ERP                    # 查询 ERP/MES/BOM 物料标准
Tool_Trigger_Alert                # 异常时触发飞书/钉钉告警
Tool_Prepare_Assembly_Simulation  # BOM 一致时调用装配仿真预备接口
```

### 5. 记忆与持久化 Memory

系统实现了两类记忆：

```text
短期记忆：记录当前批次/工位已识别构件，防止重复识别和重复告警
长期持久化：保存 Agent 轨迹日志、批次报表和关键决策记录
```

持久化设计重点：

```text
JSONL：记录每一次 Agent 执行轨迹、工具调用、推理结果和决策状态
CSV：导出批次报表，并对长物料 ID、时间戳、批次号做文本化保护
```

## ReAct 工作流

```text
Trigger：产线传感器或接口触发新构件到位
  -> Perception：调用 Tool_Read_Pipe_Text 和 Tool_Analyze_Shape
  -> Reasoning：Controller Agent 生成执行计划
  -> Validation：调用 Tool_Query_ERP 查询 BOM
  -> Conditional Reasoning：
       如果 OCR 低置信度或 BOM 查无物料
       -> 调用 Tool_Semantic_OCR_Correction
       -> 应用高置信度纠错结果
       -> 二次查询 BOM
  -> Agentic RAG：
       BOM 通过后检索最新工艺变更单/质检补充通知
       -> 调用 LLM 判断是否存在临时复检、禁装或替代料要求
  -> Decision：
       一致：记录日志，调用装配仿真预备接口
       工艺变更拦截：触发告警，挂起人工审核
       异常：触发告警，挂起状态，等待人工审核
       重复：跳过，避免重复告警
```

## 技术难点与解决方案

### 难点 1：传统 OCR 无法理解工业语义

工业现场常见 OCR 错误包括：

```text
Q345B -> 0345B
DN500 -> DN5OO
Q235B -> 0235B
304L -> 3O4L
```

传统编辑距离只能计算字符串相似度，无法判断哪些纠错在冶金和船舶制造语境下是合理的。

解决方案：

```text
引入 DeepSeek-V4-Flash 作为语义纠错模型，
将 OCR 原始文本、置信度、BOM 候选物料、工位、形状上下文和领域规则传给 LLM，
要求其输出结构化 JSON，并只在置信度达标时应用纠错。
```

### 难点 2：LLM 不能直接替代业务规则

工业质检场景不能让 LLM 直接“自由判断是否放行”，否则不可控。

解决方案：

```text
采用规则状态机 + LLM 工具的混合架构。
状态机负责确定性流程和最终业务分支；
LLM 只负责语义 OCR 纠错这类规则难以覆盖的局部任务；
所有 LLM 输出都必须经过置信度阈值和 BOM 二次校验。
```

### 难点 3：Agent 决策需要可追溯

工业现场需要知道每一次告警、放行或挂起的依据。

解决方案：

```text
为每次 Agent 执行生成 run_id；
记录每个阶段的 trace event；
保存 OCR 原始结果、LLM 纠错结果、ERP/BOM 查询结果和最终决策；
通过 JSONL 和 CSV 形成可审计轨迹。
```

### 难点 4：重复识别导致重复告警

同一根钢管可能因为摄像头多帧采集被重复识别。

解决方案：

```text
基于工位、构件 ID、物料号和形状结果生成短期记忆签名；
已处理构件再次出现时直接走 duplicate 分支；
减少重复告警和重复报表记录。
```

## 项目亮点

1. 不只是调用 OCR，而是将工业视觉能力包装为 Agent Tools，形成可编排、可扩展的智能体系统。
2. 引入 DeepSeek-V4-Flash 做语义级 OCR 纠错，解决传统规则和编辑距离难以处理的工业字符混淆问题。
3. 采用“规则状态机 + LLM 局部推理”的工程架构，兼顾工业系统的确定性、安全性和 LLM 的语义理解能力。
4. 实现 ERP/BOM 二次校验机制，避免 LLM 纠错结果未经业务系统验证就直接放行。
5. 支持异常告警和 Human-in-the-loop，将不确定或不一致状态挂起等待人工审核。
6. 具备完整 Agent 轨迹持久化能力，便于审计、复盘和后续优化。
7. 考虑工业报表落地细节，对 CSV 中的长编号和时间戳做文本化保护，避免 Office 科学计数法导致数据失真。

## 面试讲法

面试官如果问“这个项目为什么算 Agent”，可以这样回答：

```text
原来的系统只是一个 OCR API，输入图片，输出识别结果，本质上是被动感知。
我后续把它重构成了一个工业质检 Agent：
第一，它有工具系统，把 OCR、形状识别、ERP 查询、告警和仿真接口都封装成 Tool；
第二，它有状态机工作流，能够根据不同状态主动决定下一步调用哪个工具；
第三，它有 LLM 推理能力，在 OCR 低置信度或 BOM 查无物料时调用 DeepSeek 做语义级纠错；
第四，它有记忆和持久化，能够避免重复识别，并记录每一次决策轨迹。
所以它不只是识别模型，而是一个能感知、推理、校验和行动的工业 Agent。
```

面试官如果问“为什么要用 LLM”，可以这样回答：

```text
因为工业 OCR 的错误不是单纯字符串问题，而是语义问题。
比如 0345B-DN5OO，从编辑距离看可能有很多候选，但结合船舶制造和冶金常识，
Q345B 是常见低合金高强度结构钢，DN500 是合法管径表达，
再结合 BOM 候选项，LLM 能给出更符合业务语境的纠错判断。
但我没有让 LLM 直接放行，而是让它只输出结构化纠错建议，
最终仍然要经过 BOM 二次校验和状态机决策。
```

面试官如果问“怎么保证安全性”，可以这样回答：

```text
我做了三层约束：
第一，LLM 只作为 Tool 被调用，不控制整个流程；
第二，LLM 输出必须是结构化 JSON，并带有 confidence 和 reason_summary；
第三，纠错结果必须通过置信度阈值和 ERP/BOM 二次校验，才能进入放行流程。
如果不满足条件，系统会触发告警并挂起，等待人工审核。
```

面试官如果问“为什么要做 Agentic RAG”，可以这样回答：

```text
因为 ERP/BOM 是结构化且相对静态的，但制造现场经常会临时下发工艺变更单或质检补充通知。
这些内容往往是 PDF、Word 或通知文本，规则系统很难及时覆盖。
我把这些非结构化文档接入 RAG，在 BOM 校验通过之后再做一次文档审查。
例如 316L 管材在 BOM 中完全匹配，但当天工艺通知要求送二号实验室超声波复检，
Agent 会根据 RAG 审查结果覆盖常规放行路径，触发告警并挂起人工审核。
这样系统就具备了类似工程师“读最新通知再决定”的能力。
```
